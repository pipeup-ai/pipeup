An agent on your computer answers comments, the first time

On 19 October a local agent (pi, running a model in Ollama) tried to answer comments on a wiki that shows its Markdown notes through one viewer page, wiki/viewer.html?file=…. It never got a reply onto the page. Every step it was given had a gap of its own, so fixing any one of them would not have been enough. This spec closes all four, without changing what the page or the reviewer sees.

What changes

  • The commands an agent is given ask npm for any release that answers them (pipeup@0), not only the page's exact one, and never stop to ask "Ok to proceed?". Some computers only accept packages a few days old; on those, an exact new version can't be installed at all.
  • The copied text names the page's own HTML file to pass as --page (here wiki/viewer.html, not the note it shows), and says where the replies will be written.
  • pipeup reply writes nothing when it is given a file Pipeup doesn't run on, and names the page that does. It always writes where the page reads, and says so.
  • pipeup agent --page lists the agent on the page in one step, after the author's yes. Today it prints an attribute to paste into the HTML by hand.
  • Reading the comments without a browser is the open hand-off spec (#96): Copy for my agent carries the comments, so this spec doesn't change step 1.

What broke on 19 October

Four steps, each enough to stop the agent. Two of them showed an error; two would have failed quietly.

StepWhat happenedWhy
Running the commandnpx pipeup@0.8.1 reply … stopped with "No matching version found for pipeup@0.8.1 with a date before 10/16/2026".That computer's npm only accepts packages at least three days old. The copied text names the page's exact release, and 0.8.1 was a day old.

What the agent is given

Step 3 of the copied text, for Sam's wiki opened from this computer. Only the changed lines are shown; steps 1, 2 and 4 stay as they are (step 1 as #96 rewrites it).

Today
3. Answer in each thread: `npx pipeup@0.8.1 reply --page <the page's file> --thread <Thread id> "what you changed and where" --addressed "short note"`. That writes file:///Users/sam/wiki/viewer.replies.js. The page doesn't list your key yet: run `npx pipeup@0.8.1 agent --name <your name>` and tell me the attribute to add.
The exact version can't install where npm accepts only older packages, and nothing says which file is "the page's file".
Proposed
3. Answer in each thread: `npx --yes pipeup@0 reply --page /Users/sam/wiki/viewer.html --thread <Thread id> "what you changed and where" --addressed "short note"`. Pass that file, the one that runs Pipeup, not the note it shows. It writes /Users/sam/wiki/viewer.replies.js, which the page reads by itself. The page doesn't list you yet. Ask me first; after my yes, run `npx --yes pipeup@0 agent --name <your name> --page /Users/sam/wiki/viewer.html --yes`.
Opened from this computer, the page knows its own file and names it. Served from a site, it names the address instead: "the HTML file your site serves at /wiki/viewer.html". A pre-release page keeps its exact version (testers want the pre-release), and the text says to use pipeup@0 if npm refuses it.

Listing the agent

One command makes the agent's key if it has none and adds it to the page. It shows the one change and asks first. In a shell that can't ask (an agent's), it changes nothing and says why.

Run by the agent, before a yes 
$ npx --yes pipeup@0 agent --name Muse --page wiki/viewer.html
Muse (~/.pipeup/agent.json)

This adds one attribute to wiki/viewer.html, and changes nothing else:
  <html lang="en" data-pipeup-doc="…" data-pipeup-agents="3SOh…Zf4">

This shell can't ask, so nothing was changed.
Ask the page's author. After their yes, run it again with --yes.
After Sam's yes 
$ npx --yes pipeup@0 agent --name Muse --page wiki/viewer.html --yes
Muse (~/.pipeup/agent.json)
Listed Muse on wiki/viewer.html. The page now shows Muse's replies.
Run by Sam in a terminal, the same command asks "Add it? (y/N)" instead. Already listed, it says so and changes nothing.

Answering

The reply command writes only to a page that runs Pipeup, writes where that page reads, and ends with what happens next.

Given the note 
$ npx --yes pipeup@0 reply --page wiki/syntheses/q3-plan.md --thread fTU-4_Frh0j… "Changed Related Pages to links that open in the viewer." --addressed "Links updated"
wiki/syntheses/q3-plan.md doesn't run Pipeup, so nothing was written.
The page that shows it is probably wiki/viewer.html:
  --page wiki/viewer.html
It looks for an HTML file with Pipeup in the same folder and the folders above it. When it finds none, it says to pass the page the comments were left on.
Given the page 
$ npx --yes pipeup@0 reply --page wiki/viewer.html --thread fTU-4_Frh0j… "Changed Related Pages to links that open in the viewer." --addressed "Links updated"
Wrote 2 entries to wiki/viewer.replies.js.
The page reads this file: the reply shows in its thread within a few seconds.
Not listed yet 
$ npx --yes pipeup@0 reply --page wiki/viewer.html --thread fTU-4_Frh0j… "…" --addressed "Links updated"
Wrote 2 entries to wiki/viewer.replies.js.
The page will ignore them until it lists Muse. Ask the page's author. After their yes, run:
  npx --yes pipeup@0 agent --page wiki/viewer.html --yes
The replies are written anyway, so nothing is lost: once Muse is listed and the page is reloaded, they show with no second reply.

Spec wording

The changes to docs/FUNCTIONAL_SPEC.md, section 15b. Red lines go, green lines come in.

15b · Showing that a page is ready for an agent
Its commands name the version of Pipeup the page runs (`npx pipeup@0.8.0-beta.4 …`), so the agent runs the same release as the page and not whatever npm calls stable, and a pre-release's prompt points at the pre-release guide.
Its commands run anywhere an agent does: they never stop to ask (an agent can't answer), and they ask npm for any release that answers them, not only the page's exact one, because some computers accept only packages a few days old. A pre-release page's commands name its pre-release, say to use any release if npm refuses that one, and its text points at the pre-release guide.
The copied text names the page to answer on: the HTML file that runs Pipeup (its full path, for a page opened from this computer, or its address on the site), never a file the page shows (a viewer at viewer.html?file=notes.md is viewer.html). It says where the replies will be written and that the page reads them from there.
When the page doesn't list an agent, the copied text tells the agent to ask the author first and, after a yes, list itself with one command.
15b · The commands an agent runs (new)
The reply command writes only to a page that runs Pipeup. Given any other file (a note a viewer shows, say), it writes nothing, says why, and names the page nearby that runs Pipeup when there is one.
It writes the replies where the page reads them (next to the page, or the file the page names) and says where, and that the page will show them within a few seconds.
When the page doesn't list the agent yet, it still writes the replies, so nothing is lost, and ends by saying the page will ignore them until it lists the agent, with the one command that lists it.
The agent command, given a page, lists the agent on it: it makes the agent's identity if there is none, shows the one change (an attribute on the page's html tag) and asks first; with --yes it doesn't ask. Where it can't ask, it changes nothing and says to ask the author. It changes nothing else in the page, and says so when the agent is already listed.
Every release from 0.6 on reads and writes replies the same way, so any of them answers any page. A release that doesn't know an option says so and carries on with the rest.
15b · What agents are told
An agent passes the page named in the copied text and, when it can't tell which file runs Pipeup, asks instead of guessing a file the page shows. It lists itself on a page only after the author's yes.
The skills, llms.txt, the Markdown copies and the site give the same commands as the copied text, in the same form.

Open questions

1. Which version should the commands ask for?

Recommended: pipeup@0 on a stable page, any 0.x release npm will give. It installs everywhere, and every release from 0.6 answers agent, reply and comments the same way. Keeping the exact version with a fallback line instead would fail first and recover second, on every computer with an age rule.

2. Should the agent list itself, or the author?

Recommended: the agent, with --page … --yes, after the author's yes in chat. The author keeps the decision and never edits HTML. The alternative keeps today's "tell me the attribute to add", which is where people stop.

3. Should reply refuse when the page doesn't list the agent?

Recommended: write anyway and say so. The work is kept, and the replies show once the agent is listed and the page reloads. Refusing would make the agent run every reply twice.

4. When does this ship?

Recommended: as 0.8.2, from main. Local agents are broken today on any computer with an npm age rule. The hand-off spec (#96) is for the next milestone, and changes the same sentence: it would build on this one.
