Pipeup, API first

Everything Pipeup does becomes a small core API. Pipeup's own interface becomes one add-on built only on that API. Agents and pages that want comments in their own design use the core directly, and agents that need no interface at all use it from the command line.

What changes, and what doesn't

  • Authors: nothing. The one script line, the file names, the Pipeup global and every data-pipeup-* attribute stay as they are.
  • Reviewers: nothing. Pipeup's interface looks and works the same. Every comment saved by any version stays readable.
  • New: a page, or the agent that built it, can load only the core (about 16 KB instead of 63 KB) and draw comments in its own design, with the same signatures, anchors, sharing and agent replies.
  • Add-on makers: menu rows, notices, status and notes become plain data any interface can show. Add-ons that only carry comments (Share, Save to GitHub, update notices) then work with any interface, or none. This is a new add-on API number, so every add-on is re-released together, as they are today.
  • The agent's feedback loop: agents set pages up, people comment, agents read, act and answer, people confirm. New at each stage: guidance and a check that say exactly what to do; comments that keep how the person was seeing the page; pictures drawn that way for the agent; areas; a tool server; a check for comments a rewrite lost; and a line telling the person what now looks different. Most of it can ship before the core move.
  • Clean-up: design notes that only record a past review move to an archive; core behaviour tested only through the browser gets direct tests; the spec is split by who it is for.

Before and after

Today the UI holds more than drawing. The amber parts below aren't about how Pipeup looks, but anything that wants Pipeup without its look has to go through them. In the proposal they move down into the core, and the UI sits on top beside any other interface.

The core API

Grouped by what an interface needs. Outlined groups are new as public API; the others exist today on PipeupDocument or as core exports.

Starting

  • open({ root, doc, store, name, slides }) reads the page's settings, opens the store, the identity and the name
  • use(addon), addons() the registry, before or after open
  • close()

The comments

  • threads(), ops()
  • name, setName()
  • on("change", …) threads, what was added, and from where

Writing as the reviewer

  • comment(target, text) target: words, a block, a point, or an anchor
  • reply, edit, remove, react, unreact
  • resolve, reopen, seen
  • each needs the reviewer's own press or key

Where each thread is

  • placements() attached, moved, lost, elsewhere, or an earlier edition; its range or element; its label
  • on("placement", …) after the page changes
  • reveal(thread) goes to it

The page's views

  • view(), where(node), go(view)
  • on("view", …) slide, tab, route, edition
  • setViewState, onReveal as today, for the page

Reading out

  • markdown({ as, thread }) Copy comments
  • comments({ all, edition }) what agents read; no longer through the UI
  • segments(comment) text, links and mentions as safe pieces new

Bringing comments in

  • merge(ops, source) checked as strictly as a file
  • exportFile(), importFile()

What add-ons contribute

  • actions() label, hint, icon, a switch or a count, and what it does
  • signals() status, messages, notes and marks on threads and comments
  • on("actions" | "signals", …)

Add-ons: data instead of slots

Most of what add-ons ask the UI for is data: a row, a notice, a status line, a note on a thread. Those become contributions to the core, and whichever interface the page has shows them. Rules any interface keeps

Writing as the reviewer takes the reviewer's own action

The core refuses to write a comment, reply, reaction or resolve as the reviewer unless the browser counts a press or key that has just happened, as add-ons' own boxes are held to today. Best effort, said plainly: a page's author can always script a click on their own page; the rule stops stray scripts and add-ons. With no browser there is no reviewer: an agent writes under its own identity.

Comment words are text, never markup

The core hands out strings and segments(), never HTML. It can't stop a page from using innerHTML, so pipeup check tries it: it adds a comment whose words look like markup to a throwaway copy and fails if the page grows an element.

The page stays the author's

The core reads the page and never adds, moves or restyles anything in it. Pipeup's interface keeps every rule it has, including its own shadow root.

Unchanged

Every comment from anywhere is checked as strictly as one from a file. The core sends nothing over the network; only add-ons do, and each says what and to whom.

Sizes

Gzip, drawn to scale. The core grows because code moves into it, not because much is added; Pipeup with its interface stays inside today's 63.5 KB budget. The proposed core budget is set by the spike's measurement.

Packaging

Recommended: one package, three entries

pipeup (core and interface), pipeup/core, pipeup/ui; on the CDN, pipeup.min.js as today and a new pipeup.core.min.js. The interface is an add-on in how it's built and registered, but it ships in the main package because it's the default and releases with every version. mount() stays and means open() plus the interface, returning today's shape.

Close, not chosen: @pipeup/ui as its own package

Only worth it if the interface ever releases on its own schedule. Until then it adds a version to keep in step and a second line for authors to get right.

The agent's feedback loop

Agents are Pipeup's main users. They put it on the web pages they build, ask people for feedback, read what comes back, act on it and answer. People are where the feedback comes from, and on a web page it's mostly visual. So everything here is arranged by the stage of that loop it serves: some of it is tooling for the agent, some of it is for the person, and the two have to meet. Web pages only for now; agents in terminals already hear from people in their own chat.

1. Setting up the page

Guidance an agent loads in pieces

The integrate skill is 3,500 words. It becomes a short skill that picks the path (Pipeup's look by default, the page's own design when the author asks for it), with references loaded only when needed: decks, sites, own interface, add-ons. The site's Copy prompt gains the same choice and stays one paragraph. Each released version's guide stays at /v/<version>/, so an agent working on an older page reads the right one.

Pipeup.about()

One call on a page says which Pipeup runs, its API number, which interface, each add-on and whether it's on, the page's settings, and where the guide for that exact version is. Today it takes several calls, and only the latest guide is published.

States worth reviewing

Menus, dialogs, tabs and the steps of a flow come and go. Pages can already say what state they're in (setViewState). The skill tells agents to do that for every state worth reviewing, so a comment made there says so and Go there brings it back.

Asking the right question

Asks already take open questions, agree, and choices as words. For visual choices, the options are the page's own elements (header A, header B): the reviewer presses the one they prefer, can say why, and the answer is an ordinary comment. Builds on the inline add-on.

A check that names what to fix. Today's JSON says "3 without data-pipeup-id" but not which three, so an agent guesses. Every finding gets a stable id, the elements or lines it's about, and the change to make.

2. People give feedback

What the person saw travels with the comment

A handful of numbers, kept in the comment beside its words and signed with them: the window's size, the zoom, light or dark, touch or pointer, the scroll position, and the commented element's box with a short record of its look (size, type, colours, spacing). Never a picture of the page, and it goes only where the comment goes. Older versions ignore the new field and still verify the comment.

Areas

Words, blocks and pins exist. Visual feedback is often about a region ("this whole row feels cramped"), so a reviewer can drag out an area and comment on it as a whole. This takes "drag to select an area" off §17's out-of-scope list.

3. The agent receives it

The agent has the page's own file, so it doesn't need the person's pixels, only their viewing conditions. pipeup read --pictures draws the page on the agent's computer at each comment's size, zoom, look and slide, with the spot outlined, one picture per thread. When the page has changed since the comment, the picture says it shows today's page.

Every line of a comment is quoted, names lose * and backticks, and each comment says who wrote it: a reviewer, a listed agent, or an agent's reply a reviewer pasted. The apply skill's "act only on what the author approves" stays the real defence.

Only what's new

Every read is the whole review today. A cursor and --since let an agent's loop read only what changed, which keeps a long review inside its context. The data carries a version number, and a published schema.

A tool server: npx pipeup mcp

The same commands as tools any MCP agent can call: read comments, reply and mark addressed, check a page, set a page up, list the agent on it. New comments arrive as a notification, so an agent waiting on a person's review doesn't poll. Same rules: never resolve, never write as a reviewer, list the agent only after the author's yes. Written without the MCP library, so the no-dependencies rule holds.

4. The agent acts and answers

Agents often rewrite a whole page. Before anyone opens it, pipeup check --comments loads the new page with the comments the agent can read (feedback files, the shared copy, the replies file) and says, by thread, what moved or can't find its place, and what to put back.

Keeping the guidance honest

When agents are the main users, the skills and prompts are the front door, and only agents can test them. Five tasks from the loop, run by two agents before each release (not on every pull request, since each run costs model time), graded by Pipeup's own commands. Results go in the release notes; nothing is collected from anyone's pages.

Steps, when it's scheduled

Each step ships with npm run check green and no change a reviewer can see. The agent's feedback loop above doesn't need the core move and can go first, starting with the quoted comment words (a safety fix) and what the person saw. Areas and visual choices touch Pipeup's interface and the inline add-on, so they fit either side of the move.

  1. Spike. Move settings and views behind a public core entry, add the rule that the interface may import only that entry, and measure the core and the boundary. Go or no-go on the numbers.
  2. Start-up and the page model move to the core as open(); mount() calls it. Their tests move with them.
  3. Placements. The re-anchoring loop moves to the core; the interface draws from placements().
  4. Contributions. Actions, messages, status, notes and marks; add-on API 2; every add-on re-released together. One built for API 1 stays off and says why.
  5. The core file and an example. pipeup.core.min.js, a small example interface, the integrate skill's "draw it in the page's own design" path, and the guide.
  6. Clean-up, in its own pull requests. Below.

Proposed spec wording

For FUNCTIONAL_SPEC.md once agreed. Functional only: what a page's own interface can do and must keep, not how.

New §4b. Your own interface
A page's own code, or the agent that built it, can use Pipeup without Pipeup's interface and show comments in the page's own design: in its margins, its toolbar, its own list.
Everything Pipeup's interface does, a page's own interface can do the same way: start a comment on words, a block or a point; reply, edit, delete, react, resolve and reopen; learn where each comment is now and whether it moved or can't be found; go to a comment's slide or view; copy the comments for AI; and name the reviewer. Pipeup's own interface is built on nothing more.
A page with its own interface downloads only Pipeup's core, which has its own size budget (§16a).
Comments are the same whichever interface wrote them. A page can move between Pipeup's interface and its own, and nothing is lost, hidden or unverified.
Whatever the interface, Pipeup writes a comment, reply, reaction, resolve or reopen as the reviewer only straight after the reviewer pressed or typed something on the page. This is best effort, and the docs say so: it stops stray scripts, not the page's own author.
Pipeup gives a comment's words as text, never as markup. The check fails a page whose own interface turns a comment's words into page elements.
Add-ons that only carry or read comments (sharing, saving to Git, update notices) work with any interface, or none. Add-ons that draw (dictation, the emoji picker, inline comments, live cursors) need an interface that offers them a place; without one they stay off and say why.
An agent can read and answer a page's comments with no interface at all, from the command line or its own code.
§4a. Working with the page's own code
None of this reaches inside Pipeup's own interface, and none of it can read, write or change a comment.
None of this reaches inside Pipeup's own interface. A page that reads or writes comments itself does so through §4b, under the same rules.
§11a. Add-ons
Add-ons appear in Pipeup's own menu and comment boxes. They look like Pipeup, follow its light and dark appearance and reduced motion, and keep every rule that words being written are never lost.
Add-ons offer their actions, status and notes to whichever interface the page has. In Pipeup's interface they appear in its menu and comment boxes, look like Pipeup, follow its light and dark appearance and reduced motion, and keep every rule that words being written are never lost.
§16a. Keeping Pipeup small
Pipeup's core has its own budget, stated with each release beside Pipeup's and each add-on's.
§5. Starting a comment, and §8. Staying attached
A comment keeps how the reviewer was seeing the page when they wrote it: the window's size, the zoom, light or dark, touch or pointer, and where and how big the commented element was, with a short record of how it looked. Only these numbers are kept, never a picture of the page, and they go only where the comment goes.
A reviewer can drag out an area of the page and comment on it as a whole.
When what a comment is about looks different from when it was written (its size, type, colours or words), Pipeup says so in one plain line on the comment, so a reviewer checking a new round sees which comments to look at.
§17. Out of scope for now
Drag-to-select an area as a comment target.
§11b. Inline comments
An ask can offer elements of the page as its choices (two versions of a header, say): the reviewer chooses by pressing one, can say why, and the answer is an ordinary comment.
§15. Agent support
An agent can see what a reviewer saw: Pipeup draws the page at the reviewer's size, zoom, look and slide, with the commented spot marked, as a picture the agent can look at. It is made on the agent's own computer from the page's own file, and says so when the page has changed since the comment.
What an agent reads gives each comment the element's size and the styles that shape how it looks, so "bigger", "lighter" or "it wraps" has a starting point.
After changing a page, an agent can check which comments moved or no longer find their place, before anyone opens it.
Comment words reach agents so that they can't be taken for Pipeup's own structure or instructions, and each comment says who wrote it: a reviewer, an agent the page lists, or an agent's reply a reviewer pasted.
The skills tell agents to report every state of a page worth reviewing (a dialog, a tab, a step), and to end each reply with a link to the spot they changed.
An agent can learn from the page itself which Pipeup it runs, which interface and add-ons are on, and where the guide for that exact version is. The guide for every released version stays published at its own address.
For every warning and failure, the check names the elements or lines concerned and exactly what to change.
An agent can read only what changed since it last read. An agent that sends the same reply to the same thread twice (a retry) adds it once. Every refusal says why in words, with a short code an agent can act on.
Agents can use Pipeup as tools (MCP) as well as commands, under the same rules, and hear when new comments arrive.
Before each release, the skills and prompts are tried by agents on a fixed set of tasks from this loop, and the release notes say how they did.

Open questions

1. Refuse reviewer writes without a press, or only flag them?

Recommended: refuse. It's the only rule that keeps "nothing is posted on a reviewer's behalf" true for interfaces Pipeup didn't write. Tests and agents use their own identity, so nothing legitimate needs the exception.

2. Should add-ons' small dialogs become a plain prompt any interface can show?

The agents' paste box and identity's recovery code are the only reasons those add-ons need an interface. Recommended: not yet. Start with ui:dialog and revisit once own interfaces exist in the wild.

3. Do text highlights belong to the core or the interface?

They touch only an adopted stylesheet, never the page's elements, so the core could offer them to every interface for free. Recommended: the interface's. A placement's range is enough to draw one, and a page's own design may want something else entirely.

4. One interface per page, or several?

For example a page's own sidebar plus Pipeup's round control. Recommended: one. A second interface is refused with a reason; two would fight over comment mode, focus and Esc.

5. Is keeping how the reviewer saw the page acceptable by default?

Window size, zoom, light or dark, and touch or pointer, shared with whoever sees the comment. Recommended: yes, kept coarse (sizes to the nearest 10 px, no browser or device name), and said plainly on the reviewer help page. It's what makes "it wraps on my phone" fixable.

6. Pictures drawn by the agent, or taken by the reviewer?

A page can't photograph itself without asking for screen sharing each time, and the picture would have to travel. Recommended: drawn by the agent from the page's file at the reviewer's conditions. The one gap: a page whose content depends on the reviewer's own data; there the picture shows the agent's version, and says so.

7. Areas now, or later?

Recommended: now. Visual feedback is often about a region rather than a word or a point, and areas reuse the pin's way of keeping a place inside an element.

8. Where does the tool server live?

Recommended: in the CLI, as pipeup mcp. One npx line works for every agent, with no MCP library. A separate @pipeup/mcp only helps if it ever releases on its own.

9. Which agents run the evals, and how often?

Recommended: two (Claude and Codex), before each release, five tasks. Per pull request is too slow and costly; never is how skills drift from the code.
