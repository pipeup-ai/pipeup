Signed pasted replies, and a new identity for each edition

Two things came out of testing with Muse, a cloud agent that makes Sam's daily briefing. Muse keeps a key between sessions but can't put a file beside the page, so its pasted replies all read "pasted by you", even when Muse could prove it wrote them. And the briefing is a fixed shell with each day's edition swapped in, so yesterday's comments turn up on today's news.

What changes

  • An agent that keeps a key can sign the replies block it gives in a chat. The reply command prints a signed block instead of writing a replies file.
  • A signed paste from an agent the page lists shows as that agent's, exactly like a reply read from the replies file: the agent's name and the AI marking, with no "pasted by you".
  • Unsigned pasted replies don't change. They still say "pasted by you", and other people in a shared copy see "pasted by Sam".
  • The agent guidance changes from "never asks to be listed for replies it can't deliver" to "asks to be listed only when it can sign its replies."
  • Why it matters: once comments are shared, Lee can tell that Sam pasted Muse's words but didn't write them, and that Muse's signed words weren't changed on the way.
  • Editions get their own identity. The publisher sets each edition's document identity (for example a new id made from the page's id and the edition date) before Pipeup starts. Pipeup doesn't change: a new document made from a template already gets a new identity (§15). The integrate skill and llms.txt spell the case out.
  • An edition attribute that scopes comments per edition inside one document is named as an open question, not a requirement.

What the publisher does
<!-- the shell, fixed --> <html data-pipeup-doc="k7Hq…:key…" data-pipeup-auto="off"> <script src="…/pipeup.min.js" integrity="…"></script> <script type="module"> // once the edition's data has loaded const [id, key] = pipeupDoc.split(":"); const h = sha256(`${id}:${edition.date}`); pipeupDoc = `${base64url(h).slice(0, 16)}:${key}`; await Pipeup.mount(); </script>

The key stays; the id becomes a new 16 characters made from the page's id and the date (Pipeup refuses a date simply appended). Shortened; the integrate skill has the exact code.

Proposed spec wording

Changes to §15 (Agent support), §15b (Answering; Showing that a page is ready; What agents are told) and §19 (Open questions). Lines not shown are unchanged from #96.

§15 · Agent support
A page that keeps one shell and shows a new edition in it (a daily briefing, say) is one document to Pipeup, so earlier comments land on matching content in the new edition, marked Moved (§8). When each edition is meant to be reviewed on its own, the publisher gives each edition its own document identity, made from the page's identity and the edition (for example its date), set before Pipeup starts. Agents that publish such pages do this, and the integrate skill and llms.txt say how.
§15b · Answering
For an agent that can't reach the page's folder, the reply command can print a signed replies block instead of writing the file. The block carries the same replies, each signed by the agent's own identity. A signature covers the reply's words, its addressed note, its thread and the page, so a changed reply, or one pasted into another page, no longer counts as signed.
§15b · Showing that a page is ready for an agent
…the page finds the replies block in it and says in words what it found (how many replies, from which agent, how many say addressed, and how many it will leave out and why…)
…the page finds the replies block in it and says in words what it found (how many replies, from which agent, how many are signed by an agent the page lists, how many say addressed, and how many it will leave out and why…). For a reply it can't count as signed, it says why: not signed, signed with a key the page doesn't list, or changed after it was signed.
Pasted replies show in their threads under the agent's name, with the AI marking (§10) and the words "pasted by you".
A pasted reply signed by an agent the page lists shows exactly as a reply read from the replies file: under the agent's name, with the AI marking (§10), and nothing more.
Any other pasted reply shows under the agent's name, with the AI marking and the words "pasted by you"; to other people in a shared copy, it says who pasted it ("pasted by Sam"). So when comments are shared, everyone can tell that the person who pasted didn't write the agent's words, and which agent replies came to the page unchanged.
The text Copy for my agent copies tells the agent how to sign its replies block when it keeps a key, and says whether the page lists it.
§15b · What agents are told
An agent never looks for comments in the page's file, and never asks the author to list it for replies it has no way to deliver.
An agent never looks for comments in the page's file, and asks to be listed only when it can sign its replies.
An agent that can't write the replies file … answers in one replies block the person can paste into the page…
An agent that can't write the replies file … answers in one replies block the person can paste into the page, signed when it keeps a key between sessions…
§19 · Open questions
Editions: whether a page should be able to say which edition it is showing, so comments are kept per edition within one document (each edition keeps its own, and earlier editions' comments can still be found), instead of the publisher giving each edition its own identity.

Open questions

1. A pasted reply whose signature doesn't check: add it or leave it out?

Recommended: add it as "pasted by you", and say why. It is then exactly an unsigned paste, which #96 already accepts because pasting is Sam's own act. Leaving it out would punish Sam for a reply that a chat window reflowed.

2. An "edition" attribute, later?

Recommended: an open question, not a requirement. A new identity per edition works today with no change to Pipeup. An attribute would add one more thing to explain and size to pay for; it is worth it only if people want to see earlier editions' comments from today's page.

3. Editions on a shared page

To check in the design note. A shell with a sharing line keeps one line for every edition. Before the skill recommends a per-edition identity on a shared page, the note confirms that each edition's comments stay apart in the shared copy, or the skill says to set sharing up per edition.
