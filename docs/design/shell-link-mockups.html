A live link made of shell commands

Ada is planning a trip to Lisbon that starts Friday. Claude, running on Ada's Mac, made the itinerary and shows it at http://localhost:3000. Ada left six comments. For Claude to read them and answer straight into the page, today's live link needs npx pipeup watch, and Ada's Mac has no Node. Every Mac already has bash, nc and openssl, and that's enough for the link.

What changes

  • A shell link. A short script for each kind of computer does the live link's job (§15c) with only what the computer came with: bash and nc on a Mac or Linux, PowerShell on Windows. The agent can read all of it before running it.
  • It sits beside whatever already shows the page: a local preview at localhost, or the page opened as a file. It doesn't serve the page, and changes neither the page nor its address.
  • The page finds the link by itself. The script leaves a small link file next to the page. Within seconds, Share with my agent appears in the menu, off until Ada turns it on.
  • Turned on, the page sends its comments to the link, one send at a time, retrying briefly if the link is busy. The script writes them to a file next to the page, which Claude reads.
  • Replies appear by themselves, with no Node. When Ada turns sharing on, the page makes a key for this session and sends it with the comments. The script tags Claude's replies with it, and the page adds tagged replies by itself, marked "through your link". Anything untagged still waits for Ada.
  • Copy for my agent names the script for Ada's kind of computer, pinned to the page's Pipeup version with its checksum. The agent fetches it; the page fetches nothing.

What stays the same

  • Nothing leaves the computer. The link listens on this computer only, accepts only the page's own address and a secret made fresh each run, and sends nothing anywhere. The page makes no network request beyond the link.
  • Share with my agent is off on every load, and its hint says what it sends and where (§15c).
  • Agents still only reply and mark threads addressed. Copy and paste (#96, #98) still works everywhere, and pipeup watch still works where Node is.
  • Core is unchanged. Everything new on the page is in the agents add-on.

Tried on this Mac

A 40-line prototype on macOS 26.7 with its own bash 3.2, nc and openssl. The page was shown by a separate local server at localhost:3000; the link listened on 127.0.0.1:7342. Windows is not tried yet.

What was triedResultWhat it means for the design
The page sends its comments to the linkArrivedWritten to trip.comments.json; plutil (on every Mac) printed the Markdown from it.
A wrong address, a wrong secret, or another site's originRefusedThe same protections as pipeup watch work in shell.
Two sends within a tenth of a secondSecond refusednc takes one connection at a time. With 0.3 seconds between sends, or one retry after 0.15 seconds, all 13 test sends arrived. The page sends one at a time and retries for a few seconds; today it gives up at once.
The link showing the page itselfFailedThe browser loads a page's scripts at the same time, and nc refused all but one. So the shell link sits beside whatever already shows the page.
Telling the page where the link is through its addressLeaked the secretCopy comments put the address, secret included, in the Markdown. So the page finds the link from a file next to it instead, and its address never changes.
Signing replies in shellNot possible on a MacmacOS's openssl (LibreSSL 3.3.6) can't make the signatures Pipeup uses.
Tagging replies with a shared key in shellWorksopenssl dgst -sha256 -hmac works on the same Mac. That is what lets tagged replies appear by themselves.

Proposed spec wording

Changes to §15c (A live link to an agent on this computer), §15b (Showing that a page is ready; What agents are told) and §15d (The agents add-on).

§15c · Starting it
The author starts a link for a page file with one command on their own computer.
The author starts a link for a page file with one command on their own computer: pipeup watch where Node is, or the shell link, a short script published with each release that needs only what the computer came with (one for macOS and Linux, one for Windows).
The shell link works beside whatever already shows the page on this computer (a local preview address, or the file itself), and changes neither the page's file nor its address. It leaves a link file next to the page while it runs, and removes it when it stops.
Like pipeup watch, it listens only on this computer, accepts only the page it was started for and a secret made fresh each time it starts, and says in words where it is and how to stop it.
§15c · Sharing is a click
A page not shown through a link has no such switch.
The switch is shown on a page shown through pipeup watch, or next to a shell link's link file, and on no other page. It appears within a few seconds of the link starting, and goes when the link stops.
The page sends one change at a time. If a send doesn't get through, it tries again for a few seconds before it turns the switch off and says the link isn't reachable.
§15c · What the agent can do
With the shell link, the agent reads the comments from the file the link keeps next to the page, and answers by giving the script its replies block, which the script writes to the replies file.
Each time the person turns sharing on, the page makes a new key for that session and sends it with the comments; it is never put in the page's file or address. The shell link marks the replies it writes with that key. Replies marked with the current session's key are added by themselves, under the agent's name, with the AI marking and the words "through your link"; to other people in a shared copy, "through Ada's link".
Any other unsigned replies in the replies file wait for the person: the page says in words how many there are and from which agent, and adds them only when the person agrees. They show as "added by you". All of them follow every rule for agent replies (§15b).
§15b · What agents are told
Copy for my agent names the way to link the page that fits the kind of computer it is on: pipeup watch where Node is, and otherwise the shell link for that system, pinned to the page's version with its checksum. The page fetches nothing itself. On a phone or tablet it names neither.
An agent on the person's computer that can run commands but has no Node uses the shell link. It checks the script against the checksum before running it, and never asks the person to install anything to answer comments.
§15d · What the add-on does
Reads the replies file (§15b), keeps only replies from the agents the author listed, and says how many it ignored.
Reads the replies file and the link file whenever it is on the page. It keeps signed replies from agents the author listed and replies marked with the current session's key, asks the person about other unsigned replies, and says how many it ignored.
Its one sentence (§11a) becomes: "Reads a replies file next to this page, and replies you paste from your agent. When a link is running on this computer, and only after you switch it on, it sends this page's comments to that link. Nothing leaves this computer."

Open questions

1. The link file runs as a script

Recommended: treat it exactly like the replies file. A page opened as a file can't read a data file next to it, only run a script, which is why the replies file is a script today. Both are loaded inside Pipeup's own area, only from the same site or the same disk, and anything that can write the page's folder could already change the page itself.

2. How tagged replies show to others in a shared copy

Recommended: "through Ada's link". Like "pasted by Sam", it tells everyone that a person's link brought the agent's words in, not that Ada wrote them.

3. Windows blocks scripts by default

Recommended: run it with the bypass for that one run, as shown, which needs no administrator and changes no setting. To be tried on Windows before this is agreed, along with whether PowerShell's listener needs any permission for a local address.

4. Linux's different nc programs

Recommended: the script checks which one it has, uses Python's own server when nc can't listen and python3 is there, says in words which it used, and otherwise points to copy and paste.

5. Pages on a website

Recommended: not for now. A page on https:// reaching this computer is blocked by some browsers and needs the person's permission in others. Pages on websites keep copy and paste.

6. Considered and left out: driving the browser

On a Mac, osascript can run code in Safari or Chrome directly, with no link at all. But it only works after the person turns on a developer setting that lets any program with permission run code in every tab, banking included. That's too much to ask for reading comments.
